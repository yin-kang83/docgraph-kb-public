# 单机约束下的大规模文本知识库工程实现

## ——流式摄入、混合检索与确定性边界的实践

> 工程报告 · 2026-11-12
> 代码与数据：见仓库根目录（数据需自备，本仓库不含判例数据）
> 说明：本文只讨论**技术实现**（存储、流水线、索引、检索、防护、性能），不讨论任何法律业务判断。

---

## 摘要

在单台 8 GB 内存、无独立 GPU 的笔记本上，如何把上亿字级别的中文文档语料组织成可检索、可溯源、可增量维护的知识库，是一个存储、I/O 与内存三重受限的工程问题。本文报告一个基于 SQLite 单文件数据库的文档知识库系统：以"单一真相源 + 可重建派生层"为核心，实现了流式 ZIP 摄入（不落盘解压）、行级清洗与去重、双路径写入（图谱路径与批量索引路径）、FTS5 trigram 标题检索与 LIKE 降级链、可插拔向量检索与 RRF 融合，以及一套 deterministic 的边界审查门（计划门 / 会话污点 / 输出过滤）。

实测结果：2014 年度语料全量摄入 4,929,300 行，保留 4,704,775 条（拒绝 2.60%、去重 1.95%），批量索引路径吞吐 1,161 行/秒，耗时 4,246 秒；FTS、标题表、引用表规模分别为 4,704,775 / 4,704,775 / 8,788,964，总耗时约 102.5 分钟，库体积 31.35 GiB（约 7.16 KB/条）。对照 2013 年度 933,174 条的既有库，规模增长 5.04 倍、体积增长 5.05 倍，单位成本基本持平。另一条"逐案建图"路径实测仅 4.1–9.9 行/秒，比批量索引路径慢 117–283 倍，本文给出该路径的适用边界。系统回归测试 90 项全通过（2.19 秒）。

**关键词**：SQLite；FTS5；流式摄入；知识图谱；混合检索；确定性防护；单机部署

## 1 引言

### 1.1 工程问题

面向专业领域的知识库，其检索需求不只是"找相似段落"，而是要把文档之间的**结构化关系**（谁引用谁、在哪一版、在哪一天）显式存下来。这类关系如果用纯文本/向量检索表达，会出现三类不可接受的问题：引用无法回指原文、时效无法判定、冲突无法发现。

构建这类系统的常规做法是引入专用检索引擎（Elasticsearch / OpenSearch）、图数据库（Neo4j）与向量库（Milvus / Qdrant）三件套，再加一层 PostgreSQL。本文的环境不允许：单机、离线、8 GB 内存、无 GPU、单人维护。因此全部能力被压进**一个 SQLite 文件**：关系、全文索引与向量都以表的形式共存，靠事务边界保证一致性，靠外部脚本保证可重建。

### 1.2 约束条件（实测）

| 项 | 值 |
|---|---|
| 机器 | HUAWEI MateBook D 2018，i5-8250U（4C8T），8 GB DDR4-2133（板载，不可升级），MX150 |
| 系统 | Windows 11 23H2，单机、离线为主 |
| 磁盘 | D: 1 TB SSD（工作盘）；E: 2 TB USB 机械盘（只读留底） |
| 运行时 | Python 3.12.14；SQLite 3.53.1（进程内）；numpy 2.3.5 |
| 数据规模 | 年度语料 ZIP 6.66 GB；单年 400–500 万行；跨年目标 2000 万行级 |
| 人力 | 单人 + AI 辅助，无专职运维 |

这套约束决定了三条硬性设计取向：**不做常驻服务**（无守护进程，按需批处理）；**不做内存索引**（所有索引必须落盘）；**不引入第二套存储**（避免跨库一致性问题）。

### 1.3 主要工作

1. **单文件多模态存储**：把文档表、图邻接表、FTS5 索引、向量 BLOB、质量台账放进同一个 SQLite 库，用 `journal_mode=WAL` 与批量事务换取吞吐。
2. **流式摄入流水线**：ZIP 成员级流式读取，不落盘解压；行级清洗、校验、去重；500 行一个事务；成员级 checkpoint；确定性 ID 保证重跑幂等。
3. **双路径写入与选型实测**：给出"逐案建图"与"批量索引"两条路径的吞吐差（117–283 倍）与各自适用场景。
4. **检索降级链与混合检索**：FTS5 trigram 标题索引作为召回层，短查询/无命中时降级 LIKE；向量后端可插拔（fake / qwen / local），RRF 融合。
5. **确定性边界门**：把"不该输出的内容"编码成可测试的状态机（ALLOW / REVIEW / DENY），而非依赖提示词；90 项回归测试约束其行为。

### 1.4 度量口径

本文所有数字分三类标注：**实测**（有命令输出/日志为证）、**估计**（有模型依据但未测）、**未知**（明确未测）。行数口径统一为"清洗后保留条数"，与"读取行数"分开报告。

## 2 总体设计

### 2.1 分层架构

```text
                    ┌─────────────────────────────┐
   输入 ZIP/CSV ──▶ │ 摄入层 ingest/               │
                    │  markdown / judgments /      │
                    │  judgments_zip / bulk_index  │
                    └──────────────┬──────────────┘
                                   │ 事务批量写
                    ┌──────────────▼──────────────┐
                    │ 存储层 SQLite（单一真相源）   │
                    │  nodes/edges/chunks          │
                    │  judgments/raw_rows/rejects  │
                    │  dedup/checkpoints/runs      │
                    └──────────────┬──────────────┘
                                   │ 可重建派生
                    ┌──────────────▼──────────────┐
                    │ 索引层                       │
                    │  FTS5 trigram / 标题表       │
                    │  引用表 / 向量 BLOB          │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │ 检索层 retrieval/            │
                    │  FTS → LIKE 降级 → RRF 融合  │
                    └──────────────┬──────────────┘
                                   │
                    ┌──────────────▼──────────────┐
                    │ 防线层 guard/                │
                    │  计划门 / 会话污点 / 输出过滤 │
                    └─────────────────────────────┘
```

分层的判据是**可重建性**：存储层是真相源，索引层的每一张表都可以从真相源用一条 SQL 重建（`build_judgment_fts`、`build_titles`、`build_citations` 都是 `DELETE` + `INSERT ... SELECT`）。因此任一派生表损坏或需要改策略，代价是可计算的，不需要回滚数据。

### 2.2 设计原则

1. **单一真相源**：同一事实只存一份，其余全部派生。
2. **失败留证**：坏行进 `rejects`、重复行进 `dedup`、可疑行打 `quality_flags`，不静默丢弃。
3. **小步可回滚**：500 行一个事务；每个 ZIP 成员结束写 checkpoint；重跑从 checkpoint 之后继续。
4. **确定性优先**：ID 由内容哈希生成，不依赖自增序列；边界判断用确定性规则，不用模型。
5. **样本先行**：全量前先 `--limit 1000` 试跑，确认字段与计数再放量。

## 3 数据模型

### 3.1 图模型（邻接表）

```sql
CREATE TABLE nodes (
  id TEXT PRIMARY KEY, type TEXT NOT NULL, label TEXT,
  source_path TEXT, span_start INTEGER, span_end INTEGER,
  version TEXT, hash TEXT, meta TEXT,           -- meta: JSON
  effective_from TEXT, effective_to TEXT, status TEXT, created_at TEXT
);
CREATE TABLE edges (
  id TEXT PRIMARY KEY, src TEXT NOT NULL, dst TEXT NOT NULL, type TEXT NOT NULL,
  source_span TEXT, version TEXT, confidence REAL, as_of TEXT, created_at TEXT
);
CREATE UNIQUE INDEX uq_edges ON edges(src, dst, type);
CREATE INDEX idx_edges_src ON edges(src, type);
CREATE INDEX idx_edges_dst ON edges(dst, type);
```

节点类型覆盖文档结构（Law/Chapter/Article/Chunk）、判例结构（Case/Court/Norm）与推理结构（Claim/Evidence）；边类型覆盖包含、管辖、引用、支持、派生、修订、替代、冲突。`edges.as_of` 记录"该引用发生在哪一天"，使同一张图能同时回答"当时适用什么"和"现在是否有效"。

唯一索引 `(src,dst,type)` 承担了幂等去重：重跑时同一关系不会重复写，也不需要在应用层维护集合。

### 3.2 文档表

文档表是批量索引路径的核心，14 个字段：

```sql
CREATE TABLE judgments (
  id TEXT PRIMARY KEY, case_no TEXT, title TEXT, court TEXT, region TEXT,
  case_type TEXT, procedure TEXT, judgment_date TEXT, cause TEXT,
  basis TEXT, full_text TEXT, text_hash TEXT, source_member TEXT, row_no INTEGER
);
CREATE INDEX idx_judgments_court ON judgments(court);
CREATE INDEX idx_judgments_date ON judgments(judgment_date);
```

主键 `id = sha256(full_text)[:32]`：内容寻址，重跑同一条数据得到同一个主键，`INSERT OR IGNORE` 天然幂等。`source_member`/`row_no` 保留回指位置，用于回溯原始行。

### 3.3 派生表

| 表 | 规模（2014 实测） | 重建方式 |
|---|---|---|
| `judgments_fts`（FTS5 trigram） | 4,704,775 | `DELETE` + `INSERT ... SELECT id,title,'' FROM judgments` |
| `judgment_titles`（id,title） | 4,704,775 | 同上，独立小表供 LIKE 兜底 |
| `judgment_citations`（judgment_id,law,article,raw） | 8,788,964 | Python 遍历 `basis` 解析后批量插入 |
| `judgment_embeddings`（judgment_id,model,dim,vector BLOB） | 原型 5,000 | 可插拔 embedder 生成 |

`judgments_fts` 的 `full_text` 列当前恒为空字符串——这是 2026-11-09 的性能决策（见 5.1），不是缺陷。派生表体积与真相源的比例是选型的关键输入（见 7.5）。

### 3.4 溯源与质量台账

| 表 | 作用 |
|---|---|
| `ingest_runs` | 每次摄入的 run_id、起止时间、计数、状态 |
| `raw_rows` | L0 原始行 JSON（可重放，可回查清洗前内容） |
| `rejects` | 被拒行 + 原因 + 原始 JSON |
| `dedup` | 重复判定记录（case_key / text_hash / kept_case_id） |
| `quality_flags` | 可疑字段标记（日期非法、正文过短等） |
| `checkpoints` | 成员级断点，支持断点续跑 |

这套台账是"坏行不静默丢"原则的载体。实测中存在一个**设计缺口**：批量索引路径只统计拒绝数量，不落 `rejects` 表（见 8.3 第 6 条），因此 2014 年的 128,218 条拒绝无法回溯原因。

### 3.5 时间维度

四个时间分离存储：事实发生日、立案日、裁判日、规范生效/失效日。规范状态是一个五态机（`not_yet_effective / in_force / amended / repealed / unknown`），边上的 `as_of` 与节点上的 `effective_from/effective_to` 组合，支持"以判决日为基准判断某规范当时是否有效"。

实测的时效力检查（2013 年 1,804,379 条引用）结果分布为：`in_force` 405,079、`not_in_registry` 1,322,688、其余三类为 0。`not_in_registry` 占 73% 说明**数据登记不全，而不是法条无效**——系统选择显式输出"未登记"而不是猜测有效/无效，这是"事实缺失即阻断、不给默认值"原则的直接体现。

### 3.6 确定性 ID 与幂等

```python
def _id(*parts) -> str:
    h = hashlib.sha256("|".join(map(str, parts)).encode("utf-8"))
    return h.hexdigest()[:32]
```

节点/边/行/运行全部用内容哈希做主键。收益有三：重跑幂等、跨库合并无需 ID 映射、相同内容天然去重。代价是调试时 ID 不可读，需要配合 `source_member/row_no` 定位。

## 4 流式摄入流水线

### 4.1 输入与约束

单年语料为 6.66 GB 的 ZIP，内部是 12 个 CSV 成员，单行最长可达数十 KB（判决全文）。约束：不能解压落盘（磁盘与时间成本都不可接受），不能把整个成员读进内存（8 GB 机器）。

### 4.2 六阶段流水线

```text
ZIP 成员清单
  → ① 流式读取（zipfile.open，不解压落盘）
  → ② 编码探测（读前 4096 字节，依次试 utf-8-sig / gbk / utf-8）
  → ③ 表头校验（必需列子集；缺列 → 整个成员 reject）
  → ④ 行级清洗（去 BOM/控制符/零宽字符、HTML 剥离、空白压缩、全角转半角）
  → ⑤ 校验（error 进 rejects；warn 进 quality_flags）
  → ⑥ 去重（text_hash 集合内存去重 + dedup 表留痕）
  → 批量写入（2000 行/批，commit 后打印进度）
```

关键实现细节：`csv.DictReader` 包在 `io.TextIOWrapper` 上逐行读取，单成员内存占用与行数无关；进度打印带 `flush=True`，保证日志可实时观察（这一点在 8.3 第 1 条有反面教材）。

### 4.3 事务、checkpoint 与恢复

- **事务粒度**：每 500 行 commit 一次（图谱路径）/ 每 2,000 行（批量路径）。粒度是吞吐与崩溃损失的折中：越大越快，崩溃重放越多。
- **checkpoint**：每完成一个 ZIP 成员写一条 `(source, member, row_no, updated_at)`。
- **恢复语义**：重跑从 checkpoint 之后继续；确定性 ID + `INSERT OR IGNORE` 保证重复写入不产生重复数据。
- **实测崩溃恢复**：本次会话接管时曾遇到既有"自动收尾进程"崩溃（见 8.3 第 3 条），因 ID 幂等，人工重跑未产生脏数据。

### 4.4 双路径设计与实测对比

系统内存在两条写入路径，这是本工程代价最高的一个设计教训：

| | 图谱路径 `ingest-judgments` | 批量索引路径 `index-judgments` |
|---|---|---|
| 每条判例写入 | Case 节点 + Court 节点 + Norm 节点 + 边 + N 个 chunk（每条 800 字）+ chunk FTS + raw_rows JSON | 1 行 judgments |
| 事务粒度 | 500 行 | 2,000 行 |
| 实测吞吐 | **4.1–9.9 行/秒**（248–596 行/分钟） | **1,161 行/秒** |
| 2014 全量预计耗时 | 约 33 小时（33.6 万秒，估计） | **4,246 秒（实测）** |
| 产出表 | nodes/edges/chunks/raw_rows | judgments + 后建 FTS |
| 适用场景 | 需要实体关系/证据链查询 | 需要文档级检索与统计 |

两条路径的吞吐差 **117–283 倍**。原因不在 Python，而在写入放大：图谱路径每条判例要写 1 个 Case 节点、约 10 个 chunk（按 8,000 字正文估算）、1 条 Court 边、若干 Norm 边，每条 chunk 还要进 FTS5 索引；批量路径每条只写一行文本，FTS 在全部行写完后再一次性构建。

**教训**：在写入放大 10 倍以上的场景，"功能更全的路径"不一定是要跑的那条。选型前必须先用 `--limit 1000` 实测吞吐，再乘数据量估工期。本次正是因为先在 1.1 万行处做了实测（约 248 行/分钟）并向用户报告，才避免了 33 小时的无效投入。

### 4.5 编码探测的边界

探测逻辑读前 4096 字节，按 `utf-8-sig → gbk → utf-8` 顺序试解码。这个策略的失效模式是：**头部为纯 ASCII 而正文为 GBK** 时会误判为 UTF-8。实测未出现解码崩溃，但抽样发现正文中 U+FFFD（替换字符）行占比：

| 数据 | 前 2,000 行含 U+FFFD | 随机 3,000 行 |
|---|---|---|
| 2014 全量 | 201 / 2,000 = 10.05% | 312 / 3,000 = 10.40% |
| 2013 全量 | 192 / 2,000 = 9.60% | — |

两年度比例一致，说明这是**上游数据的源级损伤**，不是本次入库引入的回归。系统未对 U+FFFD 做清洗（清洗会破坏原文可追溯性），保持"只呈现、不修补"，并在质量报告中记录。

### 4.6 拒绝与去重

2014 年的行级结果（实测）：

| 指标 | 数量 | 占读取行 |
|---|---|---|
| 读取行 | 4,929,300 | 100% |
| 保留 | 4,704,775 | 95.45% |
| 拒绝 | 128,218 | 2.60% |
| 重复（text_hash） | 96,307 | 1.95% |

三者相加恰好等于读取行，说明计数账本闭合（可作一致性断言）。拒绝规则是"error 级"硬失败：案号与标题同时为空、或全文为空、或编码不可解、或表头缺列。全文过短、日期非法、法院缺失等只记 warn，仍入库。

## 5 索引与检索

### 5.1 FTS5 trigram 的选型与三个实测约束

中文没有空格分词，SQLite 内置 FTS5 提供 `trigram` 分词器（按 3 字符滑动窗口建索引），适用于子串检索。选它而不是外部分词器，是因为零依赖、可落盘、可随库迁移。代价是三个必须记住的约束：

1. **查询长度 < 3 字符必返回 0**。这是 trigram 的定义域限制，不是 bug。实测 `'合同'`（2 字）→ 0 命中；`'合同纠纷'`（4 字）→ 1,260,765 命中。任何"搜不到"的排查必须先看查询长度。
2. **全文建索引进度不可控**。2026-11-09 的实测记录：933k 条 × 平均 1,270 字符正文做 trigram 索引，超过 1 小时仍未落盘，被中止。由此产生决策 `af2b126`：**FTS 只索引标题，全文检索走 LIKE 兜底**。
3. **标题级 trigram 索引规模可控**。4,704,775 条标题（平均 27.6 字符）的 FTS 与文档表一起在 4,246 秒内落盘，体积约 1 GB 量级（估计，混在总库中未单独测量）。

`build_fts` 的实现因此是：

```sql
DELETE FROM judgments_fts;
INSERT INTO judgments_fts (judgment_id, title, full_text)
SELECT id, title, '' FROM judgments;
```

### 5.2 检索降级链

```text
查询
 → 长度 ≥3：FTS5 trigram MATCH（标题）
 → 命中为空或长度 <3：judgment_titles 表 LIKE 前缀/包含（4,704,775 行的小表）
 → 仍无命中：judgments.full_text LIKE（全表扫描，最后手段，避免扫 31 GB 的重要手段是前两级）
 → 向量后端可用：与 FTS 结果做 RRF 融合；不可用则纯 FTS，不伪造结果
```

降级的价值在**延迟可控**：标题表独立成表后，LIKE 只需扫约 800 MB 的窄表，而不是 31 GB 的主表。

### 5.3 向量原型与 RRF 融合

向量层只做原型（5,000 条），设计目标是验证接口而非效果：

- 后端可插拔：`fake`（blake2b 确定性哈希，离线可测）、`qwen`（OpenAI 兼容 `/embeddings`，需 key）、`local`（sentence-transformers，可选）。
- 向量只取"标题 + 前 1,000 字"，dim 可配（默认 64），float32 小端 BLOB 存库。
- 融合用 RRF（Reciprocal Rank Fusion，k=60），避免两路分数量纲不一致。
- 幂等：`(judgment_id, model)` 主键，重复运行只补缺失项。

局限很明确：5,000/4,704,775 = 0.11% 覆盖率，未评测召回，FFT（全量向量）需要 ANN 或分片，当前未做。

### 5.4 检索延迟实测

2014 全量库（4,704,775 条标题；测量时有一次全库完整性扫描并发，数值偏保守）：

## 6 确定性边界门

### 6.1 设计动机

需要被拦截的内容往往不是单个词能覆盖的：单步合法但组合非法、先问条文再问策略、多轮对话中逐步逼近。依赖提示词拦截这类"长因果链"不可测试、不可回归。因此把边界编码成**确定性状态机**，与 LLM 完全解耦：

- 判据是代码，可单测、可回归、行为可解释；
- 失败模式是保守的（不确定 → REVIEW），不是放行；
- 不依赖模型版本，不随模型漂移。

### 6.2 计划门（plan gate）

输入是一条计划（目标 + 有序步骤 + 步骤声明的效果），输出三态：

```text
ALLOW   纯检索/引用链，无禁止效果
REVIEW  灰区（文书/策略/证据取舍）或无法识别效果 → 不默认放行
DENY    任一步骤含禁止效果，或计划终态落在禁止效果 → 整条拒绝
```

关键规则是**终态优先**：单步合法但组合终态非法时，从第一步就不放行——避免"逐步放行"的累积效应。判定实现为纯函数，13 项测试覆盖（`test_plan_gate.py`）。

### 6.3 会话污点传播

会话级状态机：一旦出现高危语境（刑事语境关键词、策略类诉求），整段会话标记 `taint`；此后即使问题表面转回普通咨询，仍按高危处理，直到会话结束。后续只允许"条文/程序"类查询通过。

这是对"先问法条再问策略"这种多轮绕过的直接建模：**污点不可逆**，把多轮状态压成单轮判定。

### 6.4 输出过滤与模板

输出生成后再次过规则过滤器（策略/量刑/证据取舍类语言），命中则改用固定模板回复。模板是配置而非字符串拼接，便于法律顾问复核与版本管理。

### 6.5 测试覆盖

| 测试文件 | 用例数 |
|---|---|
| test_retrieval.py | 24 |
| test_criminal_guard.py | 20 |
| test_plan_gate.py | 13 |
| test_session_guard.py | 9 |
| test_case_guard.py | 7 |

本次会话实测：`90 passed in 2.19s`（Python 3.12.14，pytest 9.2.0）。测试全部使用临时 SQLite，不触碰全量库，可在 3 秒内完成回归，适合作为提交前门禁。

### 7.2 全量入库结果与跨年对照

**2014 年度（实测）**

**2013 与 2014 对照**

两个关键一致性：**规模 5.04× ↔ 体积 5.05×**，说明体积模型线性可推；**单位体积 7,145 vs 7,155 B/条**（差 0.14%），说明 2014 的体积没有异常膨胀，可以直接用 2013 的经验外推 2015–2019。

另有一份 2013 库（含全文本 FTS）体积为 16.08 GiB，单位体积 18,499 B/条。同一批数据体积差 2.6 倍，原因已定位：该库的 `judgments_fts` 索引了全文（平均 1,270 字符/条），而标题版只索引标题（平均 28 字符/条）。这直接给出了全文 FTS 的存储代价：**每条约 +11 KB，4,704,775 条即 +50 GB 量级（估计）**，且构建时间不可控（5.1 第 2 条）。

### 7.3 资源占用（实测）

citations 构建阶段是内存峰值点（Python `set` 去重 8.79M 条引用）：

| 指标 | 值 |
|---|---|
| 峰值工作集 | 3,278 MB |
| 系统可用物理内存最低 | 374 MB（总 8,075 MB，占用 95%+） |
| 硬页故障速率 | ≈20,100 pages/sec |
| 磁盘读/写累计 | 125.8 GB / 36.6 GB |
| CPU 时间 | 151 s（占墙钟 26.5 min 的 9.5%）——纯 I/O/换页受限 |

结论：8 GB 内存下，千万级去重集合会把系统推入换页状态，墙钟时间由 I/O 决定而非 CPU。可行的优化方向是**用 SQLite 唯一索引替代 Python 集合**（`INSERT OR IGNORE` + `UNIQUE(judgment_id,law,article)`），把去重状态放到磁盘。本次未改，因为要求与既有实现保持一致以便对照；这是后续可量化的优化点。

### 7.4 体积与成本模型

从实测反推每条的存储成本（2014）：

```text
31.35 GiB / 4,704,775 ≈ 7.16 KB/条    （标题 FTS + 引用 + 索引）
```

其中文档正文占大头（平均 1,729 字符，UTF-8 约 5 KB），索引与引用约 2 KB。按此外推：

| 规模 | 估计体积 | 估计索引耗时（1,161 行/秒） |
|---|---|---|
| 单年 470 万 | 31 GB | 71 min |
| 六年 2,800 万 | 190 GB | 7 h（估计，线性外推） |

190 GB 在 D 盘（1 TB）内可容纳，但会挤压备份与临时空间——这是"是否继续无脑全量入库"必须回答的问题。

## 8 失效模式与工程经验

### 8.1 失败模式清单

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 摄入跑 20 分钟，日志文件 0 字节，无法判断进度 | stdout 重定向到文件但 Python 缓冲未 flush，且进度打印代码缺失 | 改为直接查库计数（`raw_rows`/`judgments`）做外部监控；后续版本必须 `flush=True` |
| 2 | `ModuleNotFoundError: No module named 'yaml'` | `cli.py` 顶层导入 `validity`，依赖 `yaml`；该依赖未安装（或未在 `PYTHONPATH`） | 用 `pip install -e ".[dev]"` 安装依赖；文档记录 |
| 3 | 自动收尾进程崩溃，FTS/标题/引用全为 0 | 同上，链式命令首个失败即退出（`finish_2014.log` 留有 traceback） | 不依赖链式自动化；人工分步执行并在每步后断言行数 |
| 4 | FTS 查询恒为 0 命中 | 用 2 字词查询 trigram 索引 | 查询 ≥3 字；测试用例固化该约束 |
| 5 | 12,000 行入库后人工估算仍差 30 倍 | 误用图谱路径做文档级任务 | 先 `--limit 1000` 实测吞吐，再算工期；功能全 ≠ 该跑 |
| 6 | 128,218 条拒绝无法回溯原因 | 批量索引路径只计数不落 `rejects` 表 | 已知缺陷；后续把拒绝样本写入台账 |
| 7 | 8 GB 机器上 citations 阶段整机卡顿 | Python 集合 8.79M 条 + 全表扫描，触发持续换页 | 改用磁盘唯一索引去重；或分批 + 中间表 |

### 8.2 性能工程经验

1. **写入放大是第一成本**。同一份数据，逐案建图（10 倍写入）与批量写入（1 倍）差 117–283 倍。任何"更有表达力"的 schema 都要先用吞吐乘以数据量算总账。
2. **FTS 构建时间不可线性外推**。933k 条全文 trigram 超过 1 小时未落盘——构建时间与索引规模呈超线性，必须设"落盘看门狗"。
3. **内存受限时，墙钟由 I/O 决定**。citations 阶段 CPU 利用率 9.5%，其余全在等待：页故障 + 磁盘。优化点应放在减少驻留集合，而不是优化 Python 循环。
4. **日志必须能实时读**。0 字节日志等于盲跑，正确做法是 `print(..., flush=True)` 或用 `sqlite3` 计数做外部观测。
5. **幂等是恢复的前提**。内容哈希主键 + `INSERT OR IGNORE` 让"重跑"成为安全的默认操作，不需要设计复杂的断点续传协议。
6. **口径要先定**。本次验收被明确为"`judgments` 行数 = `judgments_fts` 行数"，使"入库完成"成为一个可自动断言的布尔条件，而不是感觉。

### 8.3 工程纪律

- 破坏性操作（删库、杀进程、改 schema）先报影响范围再执行；
- 全量前先小样本，样本结果与全量口径一致后再放量；
- 每步留证据：数字取自命令输出或日志 JSON，不手抄；
- 失败即停：非零退出、计数不一致、日志异常，先查明再继续。

## 9 讨论

### 9.1 局限

1. **无全文 FTS**。当前 FTS 只索引标题；全文检索退化为 LIKE 全表扫描。重建全文 FTS 的代价（+50 GB、构建时间不可控）与收益（全文召回）尚未量化决策。
2. **完整性检查成本高**。`PRAGMA quick_check` 在 31 GB 库上耗时 695.6 s（约 11.6 分钟），期间持续页换页；完整的 `integrity_check`（比 quick_check 更严格）未做。当前完整性证据 = quick_check ok + 行数断言 + FTS/标题一致性。
3. **拒绝样本不可回溯**（8.1 第 6 条）。
4. **向量层是原型**：覆盖率 0.11%（5,000 / 4,704,775），未评测召回，未做 ANN。
5. **单机并发能力为零**：WAL 支持多读单写，但没有服务化、连接池、任务队列；批处理期间无法对外提供稳定检索。
6. **数据源质量**：约 10% 行含源级 U+FFFD 损伤；系统选择不修补。

### 9.2 后续工作（按优先级）

1. 决策全文 FTS：先做 10 万条全文 trigram 的构建时间与体积实测，再外推。
2. 把 citations 去重改为磁盘唯一索引，压低内存峰值，验证 8.1 第 7 条的优化收益。
3. 补 `rejects` 落盘，使拒绝可回溯，形成真正的质量报告。
4. 六年语料（2015–2019）入库，按 7.4 的模型预估 190 GB / 7 小时，需先确认磁盘与备份策略。
5. 向量层从原型走向可用：先建 1 万条评测集，再决定是否引入 ANN。

## 10 结论

本文报告了一个在 8 GB 内存单机上，把数千万行级中文文档组织成可检索、可溯源知识库的工程实现。核心结论有三：

1. **单文件 SQLite 足以承载"文档 + 图 + 全文 + 向量 + 质量台账"的混合负载**，前提是把索引层设计成可从真相源重建的派生层。31 GB 库、470 万文档、880 万引用在单机上可管理。
2. **吞吐差异来自写入放大而非语言/工具**。逐案建图与批量索引差 117–283 倍；选型必须由实测吞吐乘以数据量决定。
3. **可测试的确定性规则是防护的基础**。把边界编码成可回归的状态机（90 项测试、2.19 秒），比依赖提示词更可维护、更可解释。

系统的规模已到"必须做工程决策"的门槛：下一个百 GB 的增量之前，需要先回答全文 FTS 与磁盘预算两个问题，而不是继续线性扩容。
